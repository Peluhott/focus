## Testing: don't

The user does all the testing themselves. When implementing:

- Do **not** run tests (`npm test`, `node ace test`, Japa), browser or e2e checks, screenshots, or live API probes.
- Don't write new tests unless asked.
- Writing the code and, at most, a quick typecheck (`npm run typecheck`) is enough. Then start `npm run dev` and hand over.
- Say plainly what wasn't verified.

## Conventions

- Every user has one or more workspaces (`workspaces` table: `name`, `position`, `ai_ack_required`; `kind` is `personal`/`work` for the two defaults, null for ones the user made). They can add, rename, reorder and delete them (`/workspaces`, session only) but always keep one (`409 last_workspace`). Deleting one cascades its data, queues its Cloudinary files for deletion, moves its month's AI spend to `ai_spend_carryovers` and keeps its `ai_consents`. Goals, projects, to-dos, notes, completions, off-track items, suggestions and the AI logs carry `workspace_id`; sub-goals, tasks, files and matches go through their parent. Data routes pick the workspace from the `X-Focus-Workspace` header: an id (what the web sends), `personal`/`work`, or a name; Personal (else the first) when missing, 404 `workspace_not_found` otherwise. Resolved via `workspace_middleware` → `ctx.workspace`. Query through `inWs` / `findInWs` / `findSubGoal`… in `api/app/services/scoped.ts`, and set `workspaceId` on create. `inList()` keys include the workspace (`todos:${ws.id}`).
- Web: the workspace list lives in the root client (`web/src/lib/workspaces.ts`, seeded by auth/me). Each workspace has its own TanStack `QueryClient` (`web/src/lib/workspace.ts`, keyed by id), so query keys stay workspace-free (`['todos']`) and every cache stays warm. `api.ts` sends `X-Focus-Workspace` from `currentWorkspace()`. The shell is keyed by workspace in `App.tsx`, so a switch resets local UI state, and it sends waiting deletes and waits for pending mutations first. The signed-in user (`me`) lives in the root client (`lib/queryClient.ts`) and is copied into each workspace's client.
- Deletes have Undo (V2-UI-CHANGES §9–10) as a *delayed delete*, not a soft-delete: `deferDelete()` in `web/src/lib/pendingDeletes.ts` drops the item from the caches, list hooks hide it via `select: useVisible(kind)`, and the real DELETE goes out when the 10 s toast (`web/src/lib/toast.ts`) ends, on workspace switch, sign-out, tab close (keepalive) or before adding/restoring a goal. Workspace deletion is the exception: confirm dialog, no Undo.
- AI on/off is per workspace (`workspaces.ai_enabled`, off by default everywhere but the original Personal; `aiActive(workspaceId)`). Turning it on where `ai_ack_required` (every workspace but the original Personal) needs `acknowledged: true` on `PATCH /settings` (else `422 ack_required`), logged in `ai_consents`. The goal (focus) limit is per workspace (`workspaces.focus_limit`, 3/5/7, set with `PATCH /settings { focus_limit }` under the workspace header; `users.focus_limit` is unused and can be dropped after the next deploy). Timer and API keys are per user.
- Adonis 6 (Node 22), not 7.
- The API returns snake_case JSON (`AppBaseModel`); web types in `web/src/lib/types.ts` match it.
- Every position write goes through `inList()` (advisory lock) in `api/app/services/ordering.ts`; client mutations share a per-list `scope` (`web/src/lib/optimistic.ts`).
- The AI (alignment check, goal suggestions and "Help me start" hints) runs on Google Gemini (`GEMINI_API_KEY` in `api/.env`), not Anthropic. All three run in the worker (`node ace align:work`) and share one circuit breaker, a global spend cap (`AI_MONTHLY_BUDGET_USD`, default $25) and a per-user cap (`AI_USER_MONTHLY_BUDGET_USD`, default $0.25). `GET /settings` returns `ai_limit` (`user`/`global`/null) and `ai_limit_resets_at`; the web shows a dismissible notice under the header (`AiLimitNotice.tsx`) and a note in Settings when a cap is hit.
- Postgres here defaults to port **5433**, not 5432: `~/.zshrc` exports `PGPORT=5433`, and the `pg` client uses `PGPORT` for any URL without a port. So the Neon URLs in `api/.env` (`DATABASE_URL`, `DATABASE_URL_DIRECT`) must say **`:5432`** explicitly (`…aws.neon.tech:5432/neondb?…`), or connections time out. `api/.env` is gitignored; if it's missing, rebuild it from `api/.env.example` with the URLs from `neon_get_connection` (project `focus`, branch `main`; pooled for `DATABASE_URL`, direct for `DATABASE_URL_DIRECT`) and add the port. Claude has DB access from this machine, so run migrations itself rather than handing them to the user.
- Deployment goes through the user's MCP tools (Neon, Render, Vercel, stack registry: `neon_*`, `render_*`, `vercel_*`, `stacks_*`). Use them for branches, env vars, deploys and logs instead of asking the user to do it. The stack is the protected `focus`.
- Run migrations with `npm run migrate`. The Render build also runs them on every deploy of `main` (`node ace.js migration:run --force --connection=migrator`), so a push to `main` migrates the shared DB. The one Neon DB is shared with the deployed app, so keep migrations additive until the new code is deployed: drop or tighten a column only after a deploy that no longer uses it (as 015 did after 013/014).
- Completions live in `todo_completions` (one row per check-off, normal or recurring); `GET /stats/completions` reads them.
- Project files are on Cloudinary (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `MAX_UPLOAD_MB` in `api/.env` and on Render). Cloudinary deletions run in the same worker (`files-delete` queue), which now starts when the AI *or* storage is configured.
- Search (`GET /search?q=`, the ⌘K palette), feedback (`POST /feedback`, stored in the `feedback` table and logged; screenshots in Cloudinary `focus/feedback`) and "done today" (`GET /stats/today?since=`) follow V2-UI-CHANGES.md §4, §5 and §7 (those addenda were folded into it).
